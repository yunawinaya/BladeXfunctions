## When a save goes async

`gdV2_onClick_save_as_created` routes ASYNC only when ALL hold; anything else calls the
original `onClick_save_as_created` unchanged:

- Save as **Created**, on a **new** GD (Add / Clone, no `id`), `ASYNC_GD_ENABLED = true`
- not built from Picking (`is_select_picking`), no line linked to a PP / Picking
- every line is a stock-controlled material (`stock_control = 1`, read from Item at click
  time) or a one-level item bundle; every line has `gd_qty > 0`
- a typed document number, or a numbering rule (sent as `"issued"`)
- at most `GD_V2_MAX_LINES = 2000` lines (bundle items counted); more → error toast

So Draft, Edit, Completed, Cancel, GDs from Picking/PP, and the Picking → GD Created path
(loading bay shuttle) all still run through `GOODS_DELIVERY` exactly as before.

## The flow

```
button ──► GD_ASYNC_SUBMIT ──► gd_async_job (QUEUED)          dialog closes here
   └─────► GD_ASYNC_WORKER (kicked once; Quartz is meant to be the safety net)
             claim job (gd_publish_step W0_CLAIM_<row_version> + 10-min lease)
             ├─► GD_BULK_PREPARE   VALIDATING → READY_TO_COMMIT / AWAITING_CONFIRMATION / FAILED
             └─► GD_BULK_COMMIT    COMMITTING_GD
                   P0 revalidate balances + SO lines
                   P1 hidden GD header + lines, gd_status 'Processing'
                   P2 on_reserved_gd + packing shell ('Processing') ── run ends (SPLIT),
                      worker calls COMMIT again
                   P3 ─► INVENTORY_APPLY_OPERATION ─► INVENTORY_LOCK_TOKENS
                   P6 barrier: operation DONE, every effect VERIFIED
                   P7A outbox GD_COMMITTED|<gd_id>|1 BLOCKED
                   P7B POINT OF NO RETURN: GD/reservations/packing → Created,
                       SO lines planned_qty + SO gd_status
                   P7C outbox READY; job GD_COMMITTED
                   (failure before P7B: hidden rows soft-deleted, job FAILED)
gd_outbox READY ──► GD_PICKING_OUTBOX_CONSUMER ─► Picking (transfer_order) + push notifications
                    job → PICKING_READY → COMPLETED
```

Each COMMIT step writes its `gd_publish_step` row STARTED before acting and DONE after a
read-back check, so a re-run resumes instead of repeating a write.

**Inventory engine.** Per allocation the GD sends an OUT `Unrestricted` + IN `Reserved` effect
pair (`movement_type GDL`) plus a verify-only `RESERVATION|<on_reserved_gd id>`. The engine
stores an `inventory_operation` + `inventory_operation_effect` rows, takes one lock per balance
in `inventory_balance_lock` (atomic-count-node, sorted keys), re-reads balances under the lock,
writes `item_balance`, `item_batch_balance` and `inventory_movement` once each, verifies the
after-values, then releases the locks. Any mismatch → `REQUIRES_REVIEW`. Same stock result as
the old save (verified against old-path GDs on dev).

## Job states (`gd_async_job.job_status`)

QUEUED → VALIDATING → (AWAITING_CONFIRMATION | CALCULATING) → READY_TO_COMMIT →
COMMITTING_GD (RECONCILING_GD) → GD_COMMITTED → CREATING_PICKING (PICKING_RETRYING) →
PICKING_READY → COMPLETED. Terminal: COMPLETED, FAILED, CANCELLED, REQUIRES_REVIEW.

## Gaps found 2026-10-08 and their fixes (in this repo; deploy to dev pending)

1. **No Picking was ever created** — nothing called `GD_PICKING_OUTBOX_CONSUMER`.
   **Fixed:** `GD_ASYNC_WORKER` calls it (`sql_node_PKjob001` → `code_node_PKdec001` →
   `if_PKcall001` → `workflow_node_PKcons01`) for a job its own iteration committed. A failed
   consumer run leaves the event READY; **its Quartz schedule (poll mode, no params) is the only
   retry path — required.**
2. **Stuck jobs** — Quartz worker rows Paused, none for 711077. **Platform config, not code:**
   resume / add the rows (see deploy notes).
3. **`gd_total = 0`.** **Fixed:** `GD_BULK_COMMIT` `code_node_KBrubvGI` computes it like
   `GOODS_DELIVERY` `code_node_IyJHrBst` (top-level rows; matches the old path: 748 = 748 on the
   same 499 lines). Jobs already past P1 keep 0.
4. **No credit-limit check on Created.** **Fixed:** `GD_BULK_PREPARE` (`code_node_CLplan00`,
   `if_CLneed000`) calls `CREDIT_LIMIT_CHECK` when `full_cl_check = 1`, with the headless "auto"
   rule: a Block → job FAILED `GD_CREDIT_LIMIT_BLOCKED` (nothing staged), an Override passes.
   The user is NOT told — the reason is only on `gd_async_job`.
5. **No reorder Redis tracking.** **Fixed:** `GD_BULK_COMMIT` step `P7E_REORDER` (after the job
   is GD_COMMITTED; at-most-once via the unique (tenant, job, step) row; never a FAILED row)
   calls `REORDER_SET_REDIS` with `organization_id`, a new optional param of that workflow, used
   only when there is no user session (a Quartz run) and only if it is digits; the session org
   always wins, so every existing caller keys exactly as before.
6. **Movements are merged per balance** (one OUT/IN pair per item+bin). Quantities correct;
   cancel of a merged async GD still to be tested on dev.
7. The click-time Item read has no `.field()` projection (slow on Item; see memory). Not fixed.

## Where to make changes now

- **Edit, Draft, Completed and the Picking/PP paths** still go through `GOODS_DELIVERY` and the
  original form handlers. Fix those as before.
- **New GD saved as Created** goes through this folder. Logic copied from the old save now
  lives in TWO places: auto allocation (`GD_BULK_PREPARE`) and picking creation
  (`GD_PICKING_OUTBOX_CONSUMER`, a port of `code_node_o35eZx2c`). A fix to either in
  `GOODS_DELIVERY` has to be repeated here, by the other developer, in their build scripts.
- `func_processGDLineItem` is still the live line handler while `STOCK_CHECK_ENABLED = false`.
  If the switch is turned on, the frozen copy in `gdV2_funcProcessGDLineItem` (dev v1444)
  replaces it and later edits to the original stop applying.
