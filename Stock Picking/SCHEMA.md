# `stock_picking` — collection spec

Sibling of `transfer_order` (the Picking document), serving the **issuing** Stock Movements:
Location Transfer, Plant Transfer, Misc Issue. Derived from the live dev schema of
`transfer_order` with the Goods-Delivery baggage removed.

These collections must be created in the platform **before** the form and workflows can be
wired — every get/add/update node needs a real `<Display Name>:Table:<id>` source.

Types below are the live `transfer_order` types, so a picked column keeps its exact type.

## 4. Setup — columns on the existing `picking_setup`

**No new setup collection.** Stock Picking rides on `picking_setup`, because every reader of that
table — `PickingSetupOnMounted`, `PickingSetupSave`, `PPonMounted`, `PPonChangePlant`,
`PPinventoryDialog`, `GDheadWorkflow`, `PickingProcessWorkflow`, `PPheadWorkflow` — filters on
`organization_id` / `plant_id` only and takes `data[0]`. Adding **rows** keyed by `movement_type`
would therefore have GD/PP randomly reading a stock-movement row, and `PickingSetupSave.js`
(`.doc(data[0].id).update(...)` per plant) would overwrite it. Columns avoid that entirely.

Five new columns, all `int`, nullable, default `0` — so the feature is **off until switched on**
and no backfill is required:

| Column | Meaning |
|---|---|
| `lot_picking_required` | master switch for Location Transfer |
| `pt_picking_required` | master switch for Plant Transfer |
| `msi_picking_required` | master switch for Misc Issue |
| `sp_auto_advance` | completing the pick advances the movement (default 0) |
| `sp_allow_full_picking` | M:N — one movement line split over several pickings |

`sp_allow_full_picking` is deliberately separate from the existing `allow_full_picking`, so turning
M:N on for Goods Delivery does not silently turn it on for stock movements.

The remaining knobs (`picking_mode`, `split_policy`, `bin_validation_scope`, the four
`require_*_scan` flags) are **reused as-is** from the GD configuration — nothing in this build
reads a stock-movement-specific variant of them.

## 5. Columns required on the SOURCE movements

Verified absent: only `goods_delivery` (header **and** line) has `picking_status`. None of the
three movement tables do, so the pick task has nowhere to record that a movement is being
picked. **Six new columns are needed** — `varchar(255)`, nullable:

| Table | Column |
|---|---|
| `sm_location_transfer` | `picking_status` |
| `sm_location_transfer_d2c7o1jd_sub` | `picking_status` |
| `plant_transfer` | `picking_status` |
| `plant_transfer_d2c7o1jd_sub` | `picking_status` |
| `sm_misc_issue` | `picking_status` |
| `sm_misc_issue_d2c7o1jd_sub` | `picking_status` |

Values mirror GD: `Not Created` / `Created` / `In Progress` / `Completed` / `Cancelled`.

The line subforms also need `prev_temp_qty_data` (`longtext`) so the pick can keep the
pre-image when it rewrites `temp_qty_data`, exactly as `PickingProcessWorkflow` does for GD.
`sm_location_transfer_d2c7o1jd_sub` and the other two currently have `temp_qty_data` but no
`prev_temp_qty_data`.
